# Authentication

Registration, verification, login, sessions, recovery, and the role model that
is deliberately not built yet.

The security rationale for each control lives in [security.md](./security.md).
This document describes the flows and the state they move through.

---

## Why this is built in-house

Two decisions are worth stating plainly, because both are usually made the
other way.

**Opaque session tokens, not JWTs.** A JWT is valid until it expires. Logging
out, changing a password, or revoking a compromised session then requires a
denylist — which is a database read on every request, which is exactly the cost
the JWT was supposed to avoid, plus a second source of truth. This product
revokes sessions on password change, on password reset, and on demand, so
revocation has to be authoritative. An opaque token is one indexed lookup and
one row to delete.

**No auth framework.** The requirements that shaped this — organization-scoped
signup that creates a tenant, a `PENDING_VERIFICATION` state that issues no
session, per-account and per-IP lockout, and a session row that carries tenant
identity into RLS — are the parts a framework asks you to override anyway. The
implementation is about 900 lines across `src/server/auth/` and
`src/server/services/auth-service.ts`, and every branch of it is tested.

## Registration

`POST /api/v1/auth/register` — organization name, admin name, email, password,
locale.

One transaction creates the tenant and its first user:

```ts
const organizationId = uuid();          // generated before the insert
created = await withTenant({ organizationId }, async (tx) => {
  await tx.insert(organizations).values({ id: organizationId, ... });
  return insertTenantContents(tx, organizationId, input, passwordHash);
});
```

The id is generated by the application rather than by `gen_random_uuid()`
because `withTenant` must set `app.organization_id` **before** the first insert
— the RLS policy on `organizations` checks it on the inserted row. There is no
moment during tenant bootstrap when the connection is unscoped.

The response is `201 { organizationId, email, requiresVerification: true }`.
**No session is issued.** The user is `PENDING_VERIFICATION` and cannot sign in
until the emailed link is opened. Verification that can be skipped is
decoration.

The slug is derived from the organization name, transliterated where needed,
and de-duplicated with a numeric suffix. Arabic names produce usable slugs
rather than an empty string.

### Where the mail goes

`sendEmail` in `src/server/services/email.ts` supports two transports.
`EMAIL_TRANSPORT=log` writes the message — including the verification link — to
the structured log, which is what development uses. With `EMAIL_TRANSPORT=smtp`
and no `SMTP_URL`, it **throws**. It never returns success without having sent
anything: a silently dropped verification mail is an account that can never be
activated, reported as a success.

## Verification

`POST /api/v1/auth/verify-email` with the token from the link.

It is a POST, and the emailed link points at a page that posts it — not a GET
that consumes the token. Mail clients, link scanners and corporate security
gateways fetch URLs eagerly; a GET endpoint would burn the token before the
recipient ever clicked.

Tokens are hashed at rest, single-use via `consumed_at`, and valid for 24
hours. Issuing a new one invalidates the previous. The token is marked consumed
only **after** the status change commits, so a failure leaves the link usable
instead of destroying it.

On success the user becomes `ACTIVE` and a session is issued — the person is
demonstrably at the address and holding the link, so a second sign-in step buys
nothing.

## Login

`POST /api/v1/auth/login`.

```
             ┌── unknown address ──┐
             │                     ├─► fakeVerify()  ─► invalid_credentials
             └── wrong password ───┘
             ── locked ──────────────► account_locked { minutes }
             ── PENDING_VERIFICATION ► email_not_verified
             ── ok ──────────────────► session cookie + 200
```

`fakeVerify()` runs a scrypt verification against a dummy hash so an unknown
address costs the same wall-clock time as a wrong password. Without it, response
latency is an account-enumeration oracle regardless of what the response body
says.

Failures increment a per-account counter. Five failures lock the account for 15
minutes. A successful login clears the counter and, if the stored hash was
produced with weaker parameters than the current policy, **rehashes in place** —
the plaintext is available exactly once, at this moment, so this is the only
place a cost increase can be applied without asking anyone to change anything.

Two rate-limit buckets run in front of it: 10 per 5 minutes per IP, and 5 per 15
minutes per email address. An IP limit alone lets a botnet spread its guesses
across hosts; an account limit alone lets one host enumerate addresses cheaply.

## Sessions

| | |
|---|---|
| Token | 32 bytes from `crypto.randomBytes` |
| Stored | SHA-256 of the token, never the token |
| Cookie | `__Host-aiw_session`, `httpOnly`, `Secure`, `SameSite=Lax`, `path=/` |
| Absolute lifetime | 30 days — a session cannot outlive this regardless of use |
| Idle timeout | 14 days without a request |
| Renewal | `last_used_at` is touched at most hourly, so activity does not cost a write per request |

The `__Host-` prefix is browser-enforced: it requires `Secure` and `path=/` and
**forbids** a `Domain` attribute, which is what stops a compromised subdomain
from overwriting the cookie. No server-side check can provide that. Locally,
where `Secure` cannot be satisfied over plain HTTP, the name falls back to
`aiw_session` — a development-only difference, in one function.

Session resolution goes through `auth_resolve_session`, a `SECURITY DEFINER`
function with a pinned `search_path` (`drizzle/0002_auth_path.sql`). It has to:
resolving a session is how the request learns which tenant it belongs to, so it
happens **before** `app.organization_id` can be set, and an RLS-scoped read
would find nothing. The bypass is confined to a handful of narrow, named
functions rather than granted to the application role as `BYPASSRLS`.

Every other read and write in the request — including issuing the session row —
goes through `withTenant` like everything else.

### Revocation

| Event | Effect |
|---|---|
| Logout | that session |
| Password change | every session, including the current one |
| Password reset | every session |

## Password recovery

`POST /auth/request-password-reset` **always** returns `200 { ok: true }` —
whether or not the address exists, whether or not mail was sent. Anything else
turns the endpoint into the enumeration oracle that login was carefully built
not to be.

Reset tokens live one hour, are hashed and single-use, and issuing one
invalidates any previous. Completing a reset revokes every session, so an
attacker holding a stolen session loses it the moment the owner recovers the
account. The rate limit is 5 per hour.

## Password policy

NIST SP 800-63B: a 12-character minimum, no composition rules, no forced
rotation — and the screening step that most implementations skip.

The screening is structural rather than a block list, because `password1234` is
twelve characters, contains letters and digits, matches no exact block-list
entry, and is among the first guesses any attacker makes. It was accepted by the
first implementation here and found in live testing.

Two independent normalizations run, and either one matching is a rejection:

- **Strip padding** — digits, years and punctuation appended to a base word.
  `password1234` → `password`.
- **Translate leetspeak** — digits standing in for letters. `p@ssw0rd` →
  `password`.

Doing them in sequence gets one of the two wrong: substituting leet first turns
`password1234` into `passwordiea`, which matches nothing. The alphabetic core is
then judged by dominance ratio, so `password!` and `Password2024` fail while a
passphrase containing the substring does not.

Independent of any word list: sequential runs, repeated blocks, all-digit
passwords, and anything containing the user's own email or organization name.

Hashing is scrypt at OWASP parameters (N=2^17, r=8, p=1) with the parameters
encoded into the stored hash, which is what makes the in-place upgrade on login
possible.

## Roles

`roleEnum` carries five values — `OWNER`, `ADMIN`, `MANAGER`, `EMPLOYEE`,
`MARKETING_MANAGER` — and every user created today is `ADMIN`.

**No permission checks are implemented.** That is deliberate (§10): the first
release is admin-only, and a permission matrix built before anyone has used the
product would be guesswork encoded as authorization logic.

What exists is the part that is expensive to add later:

- the column, the enum and the value on every row, so introducing a role is a
  permission-table change rather than a data migration;
- `session.role` resolved and carried on every authenticated request, so a check
  has something to read;
- thin route handlers over services, so an authorization gate has exactly one
  place to live.

Adding real roles means writing the permission map and calling it in `route()`.
It does not mean touching the schema, the session, or any page.

---

## What is not implemented

| | |
|---|---|
| MFA / TOTP | The session model supports it; there is no enrolment flow. |
| OAuth / SSO / SAML | `users` carries no password-only assumption that would block it. |
| Device / session list UI | Sessions are revocable through the API; nothing renders them. |
| Account deletion | Soft-delete columns exist; no self-service flow. |

## Tests

`tests/auth/registration.test.ts` (28) and `tests/auth/password.test.ts` (13)
run against a real PostgreSQL as `app_user` — a role with neither `SUPERUSER`
nor `BYPASSRLS`.

That distinction is not academic. The whole authentication path once failed
under RLS with `new row violates row-level security policy for table
"organizations"`, and it was invisible in development because development
connected as `postgres`. Running the suite as the least-privilege role is what
surfaced it; `drizzle/0002_auth_path.sql` is the fix.
