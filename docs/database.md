# Database

PostgreSQL 16. Schema in `src/server/db/schema.ts`, migrations in `drizzle/`.

---

## Migrations

| File | Purpose |
|---|---|
| `0000_init.sql` | 20 tables, enums, indexes, constraints. Generated by drizzle-kit. |
| `0001_rls.sql` | Row-level security, append-only triggers, the `app_user` role. Idempotent. |
| `0002_auth_path.sql` | `SECURITY DEFINER` functions for the authentication path. Idempotent. |

Apply in filename order. CI applies all three to an empty database on every run,
and fails the build if `drizzle-kit generate` produces a new file — which would
mean `schema.ts` had drifted from the checked-in SQL.

---

## Conventions

- **UUID primary keys**, generated with `gen_random_uuid()` or by the
  application when an id is needed before the insert (tenant bootstrap).
- **`organizationId` on every tenant table**, `NOT NULL`, FK with
  `ON DELETE CASCADE`. This is the isolation boundary.
- **Composite indexes lead with `organizationId`**, so the scoped query is also
  the fast query.
- **Money in minor units as `bigint`.** Meta's Graph API uses minor units too,
  so there is no rounding step at the boundary. Conversion happens exactly once,
  in `draftToColumns`.
- **Soft deletion** (`deletedAt`) on user-visible content. Audit logs and usage
  records are never soft-deleted; they are append-only.
- **Timestamps are `timestamptz`.** Display timezone is a tenant setting.

## Tables

### Identity

| Table | Notes |
|---|---|
| `organizations` | Tenant root. Unique slug. Default locale, timezone, currency. |
| `users` | Unique on `lower(email)` **platform-wide**, so login needs no tenant hint. Carries lockout counters and an optional locale preference. |
| `sessions` | SHA-256 of the token only. Absolute expiry plus a sliding `last_used_at`. |
| `auth_tokens` | Verification and reset. Hashed, single-use via `consumed_at`. Deliberately not RLS-protected — reached before a tenant is known, holds no tenant content. |
| `rate_limits` | Fixed-window counters keyed `<bucket>:<subject>`. Also outside RLS. |

### Agents

| Table | Notes |
|---|---|
| `agent_requests` | One row per gateway invocation — the audit spine for all AI activity and the source of every dashboard "requests" figure. Written **before** the call. |
| `agent_jobs` | Long-running work. Partial unique index on `(organization_id, idempotency_key)`, so idempotency is per tenant. |
| `conversations` | Unique `agent_session_id` — the handle to the n8n workflow's 10-turn buffer memory, generated with 24 bytes of entropy and never returned to the browser. |
| `messages` | Citations as `jsonb`, parsed from the agent's prose. `CHECK` restricting feedback to −1/+1. |

### Content

| Table | Notes |
|---|---|
| `assets` | `storage_key` points at object storage; media never lives in Postgres. Partial unique index on `(organization_id, checksum)` where not deleted, so an identical regeneration reuses the stored object. |
| `knowledge_sources` | The Drive folder the workflow indexes. `document_count` is nullable and stays null — the workflow never reports one, and the UI says so rather than showing `0`. |
| `knowledge_syncs` | Sync history. Populated by the callback endpoint when a workflow starts reporting. |

### Advertising

`campaigns` carries the most constraints, because it is the table that can cost
money:

| Constraint | Guards |
|---|---|
| `campaigns_meta_campaign_key` unique on `meta_campaign_id` | Two rows against one Meta campaign — the last backstop against duplicate spend. |
| `campaigns_launch_idempotency_key` unique on `(organization_id, launch_idempotency_key)` | A retried launch reaching Meta twice. Scoped per tenant so two organizations may reuse a key. |
| `campaigns_age_range` | 13 ≤ min ≤ max ≤ 65. |
| `campaigns_budget_positive` | A zero or negative budget. |
| `campaigns_schedule_order` | An end date at or before the start date, which the workflow's validator also rejects. |

`approved_snapshot` (`jsonb`) freezes exactly what the approver saw. Any edit
clears the approval, so what is submitted is always what a named person signed
off on.

`campaign_metrics` exists and the analytics layer computes every derived rate
correctly — but **nothing writes to it**, because the advertising workflow has
no Insights node. It is here so the schema needs no migration the day that
changes, and until then the API reports `available: false` rather than zeros.

### Platform

| Table | Notes |
|---|---|
| `usage_records` | Append-only meter (§47). Every billable event recorded from day one so a future plan/limit/credit system has real history. |
| `audit_logs` | Append-only. Actions stored as stable keys, never prose. |
| `notifications` | Stores an i18n key plus parameters, never rendered text — so a notification created in Arabic renders in English after a switch. |
| `system_events` | Platform health. Nullable tenant: some events belong to no tenant. |
| `webhook_deliveries` | Unique `nonce` — this *is* the replay guard. Records every inbound callback including rejections, which is what makes failed-webhook monitoring possible. |

## Row-level security

Covered in [multi-tenancy.md](./multi-tenancy.md). The short version: enabled and
`FORCE`d on every tenant table, fail-closed when unscoped, and the application
must connect as `app_user` — a superuser connection removes the policies rather
than weakening them.

## Query patterns

**Aggregates use `FILTER`, not several round trips.** The dashboard renders five
tiles from one scan:

```sql
count(*) FILTER (WHERE created_at >= date_trunc('day', now()))::int AS today
```

**Time series fill their gaps.** A day with no activity is a zero point, not a
missing one — a line chart that skips empty days misrepresents a lull as a
straight line.

**Derived rates guard their denominators.** `ctr`, `cpcMinor` and `roas` return
`null` rather than `NaN` or `Infinity`; a NaN leaking into the UI renders as
"NaN%" on a dashboard. Tested.

**Nothing loads unbounded.** Every list endpoint takes `limit`/`offset` with a
hard cap.

---

## Connection management

`postgres.js` with a pool of `DATABASE_POOL_MAX` (default 10) per instance.
`prepare: false` for PgBouncer compatibility in transaction pooling mode.

Both the client and the logger are **lazily initialised** behind a Proxy. Two
reasons: `next build` imports every route module to collect page data, and a
module that validated `DATABASE_URL` on import would make a production build
require production secrets; and a serverless cold start should not pay for a
pool it may never use.
